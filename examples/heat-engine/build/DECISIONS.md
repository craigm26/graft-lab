# heat-engine: decisions

Why the specification says what it says. Each decision names where its claim came from.

## D-001: The whole audit record is pinned, byte for byte

- Source: extraction
- Cited by: REQ-AU-001, REQ-WB-003, REQ-FL-002, REQ-FL-005

The earlier implementation's main cross-language guarantee was byte-equal serialized
audit records, including the human-readable `result_summary`. Pinning all of it makes the
spec nearly as detailed as the code for summaries and number formatting. Decision: pin
every audit member, including `result_summary`, number text, fixed-point text and
canonical JSON (the three edges), and member presence rules; leave error message text,
standard error and library shape open. Why: the audit record is what a downstream consumer
stores and compares; if two implementations may differ in it, byte comparison stops being
useful.

Rejected:
- Pin only the structured members and compare result_summary by pattern, as some earlier tests did: the earlier cross-language check compared whole records.

## D-002: Number text follows ECMAScript, not the host language

- Source: extraction
- Cited by: edge number-text/ecmascript, edge fixed-text/ecmascript

Canonical JSON and summaries write numbers as text. The earlier implementation used
JavaScript's `String(n)` and `toFixed`. Other languages differ: Python's `repr` writes
`1e-07` and `1e+20` where JavaScript writes `1e-7` and `100000000000000000000`; Python's
`'%.1f'` rounds exact ties to even (`20.25` → `20.2`) where `toFixed` rounds them up
(`20.3`). Decision: the edges number-text/ecmascript and fixed-text/ecmascript. Why: byte
equality across languages needs one rule; the earlier fixtures were produced with this one.

Rejected:
- Fixed significant digits everywhere: changes all existing expected bytes.

## D-003: The emitted contract version is 0.2.0

- Source: extraction
- Cited by: REQ-AU-001

Audit records carry `spec_version`, the version of the audit and behavior contract. The
earlier implementation emitted `0.1.1`, and this spec changes the contract in places, so
claiming `0.1.1` would be false. This is a different number from the document's own
version, which tracks the wording. Decision: emit `"0.2.0"` (REQ-AU-001).

Rejected:
- Keep 0.1.1: dishonest about the changes.

## D-007: Non-finite inputs are written as strings in audits

- Source: extraction
- Cited by: REQ-IF-006, REQ-AU-002, REQ-WB-004, REQ-FL-003, REQ-FL-006

The earlier TypeScript wrote `NaN` inputs as the string `"NaN"` but let `Infinity`
through, which its serializer then wrote as `null`; the other earlier implementation wrote
`"Infinity"`. Decision: `"NaN"`, `"Infinity"`, `"-Infinity"` (REQ-AU-002); requests use
the same three strings (REQ-IF-006), since JSON has no non-finite numbers. Why: symmetric,
lossless, and matches one of the two earlier behaviors.

Rejected:
- null: loses which value it was.

## D-009: RH is clamped to [5, 100], not [5, 99]

- Source: extraction
- Cited by: REQ-WB-001, PROP-WB-P8, PROP-WB-P2, PROP-WB-P3

Stull's stated validity range is RH 5–99 %; the earlier input schema said implementations
"MUST clamp to [5, 99]"; the earlier code clamped to [5, 100], and a test asserts
`RH=120 → 100`. Decision: clamp to [5, 100] (REQ-WB-001); RH in (99, 100] computes without
a marker. Why: code and tests agreed, and 100 % is a real humidity.

Rejected:
- Clamp to 99: contradicts the earlier tests.
- Mark RH above 99 as out of range: new behavior nobody asked for.

## D-010: Flag bands are in °F, and the °C path uses one exact expression

- Source: extraction, primary source
- Cited by: REQ-WB-005, REQ-FL-001, REQ-FL-004, PROP-WB-P1, PROP-FL-P1

MCO 6200.1E defines the bands in °F with inclusive lower bounds. The °C path converts
first. Floating-point error can move a value across a boundary: for `26.66666666666666` °C,
`(c*9)/5+32` gives `79.99999999999999` (white) but `c*1.8+32` gives `80` (green). Decision:
REQ-FL-004 pins `(wetBulbC * 9) / 5 + 32`; REQ-WB-005 pins `((tempF - 32) * 5) / 9`. Why:
the order of operations is observable at the boundaries.

Rejected:
- A tolerance at boundaries: makes flags ambiguous.

## D-017: canonical returns no audit

- Source: extraction
- Cited by: REQ-CJ-005

Every computing operation returns a result and an audit. The canonical serializer is a
utility, exposed so the suite can test number and string rules directly. Decision:
`canonical` responds with `result` only (REQ-CJ-005). Why: an audit of the serializer would
itself need serializing; nothing consumes it.

Rejected:
- A trivial audit: noise.

## D-018: Wet-bulb tolerance is ±1e-5 °C

- Source: extraction
- Cited by: REQ-WB-001

The imported wet-bulb fixtures carry a tolerance of 0.00001 and expected values to six
decimals, generated by evaluating the formula in double precision. Stull's own claimed
accuracy is about ±0.65 °C against observations; the tolerance here is about agreeing on
the formula, not about meteorology. Why: any faithful double-precision evaluation passes; a
wrong constant does not.

Rejected:
- A looser tolerance: would hide a mistyped constant.

## D-019: Malformed requests are errors, invalid values are results

- Source: extraction
- Cited by: REQ-IF-007, REQ-IF-009, REQ-WB-004, REQ-WB-006

The earlier library returned `invalid_input` audits for non-finite numbers and unknown
flag names, which are values a caller can legitimately pass. Missing fields and wrong JSON
types have no library equivalent once a process boundary exists. Decision: missing fields
and wrong JSON types are `bad_request`; non-finite numbers and unknown flag names are
`invalid_input` results. Why: keeps the earlier invalid-input audits intact while giving
the driver a clean failure for garbage.

Rejected:
- Turn everything into invalid_input audits: which field names would the audit carry for a missing member?

## D-021: Object keys sort by UTF-16 code units

- Source: extraction
- Cited by: edge json/sorted-utf16

The earlier serializers sorted keys with JavaScript's default comparison, which compares
UTF-16 code units. That differs from code-point order only for keys mixing characters above
U+FFFF with characters in U+E000–U+FFFF. All keys in audit records are ASCII, so it matters
only for `canonical`. Decision: the edge json/sorted-utf16. Why: one rule, matching the
earlier output.

Rejected:
- Code-point order.

## D-024: Error checks are a numbered order

- Source: r02
- Cited by: REQ-IF-007

The prose spec once said checks happen "in the order the table lists them" (the table
listed `bad_request` first) and, in the same sentence, "`unknown_op` before input checks".
The r02 builder chose the intended order and noted the wording was loose. Decision: the
order is the numbered Errors list, declared once; `duramen check` rejects a requirement that
restates it (T005).

Rejected:
- Keep a table and drop the first clause: still easy to misread.

## D-025: Infinite °F converts by the same expression

- Source: blind build t07 (choice C-7) and duramen agree, 2026-10-08
- Cited by: REQ-WB-005

REQ-WB-005 said that "a non-finite tempF gives a non-finite tempC". The t07 builder read
that as "always NaN" and wrote `"NaN"` in the audit for an infinite `tempF`, where the exact
expression gives an infinity; no case checked it, and `duramen agree` found the difference
on 199 of 400 generated `wetBulbF` requests. Decision: the text says that the expression
applies to non-finite values too, and two examples pin the infinities. Why: the expression
was already the rule; the summary sentence invited the shortcut.

Rejected:
- Treat every non-finite tempF as NaN: loses the sign the input had, and contradicts the exact expression.

## D-026: flagC's °F overflow is flagF's invalid input

- Source: Graft rebuilds oijHUuC_9S7zQaXq8032Sw (two builds) and rDROdKjpQwaa80PjFQ320A (holdout), 2026-10-31
- Cited by: REQ-FL-005

OPEN-FL-001 left open what `flagC` does for a finite `wetBulbC` whose °F conversion
overflows. Two builds of one rebuild passed every case and chose differently: one gave the
REQ-FL-006 form (`invalid_input:wetBulbC`, no children), the other kept REQ-FL-005's shape
with `flagF`'s invalid-input audit as the child. t06 and t07 had split the same way (C-5,
C-6); blind builds t01 to t05 all chose the child form, ending the summary three different
ways (`invalid_input:wetBulbF`, `invalid`, `invalid_input`). `duramen agree` saw the split
but could not judge it: the oracle read `.flag` of a `null` result and threw, as it did on 2
of the rebuild's 1,500 hidden requests. Decision: REQ-FL-005
applies to every finite `wetBulbC`, so the overflow is `flagF`'s invalid input, carried as
the child and named at the end of the summary. Examples pin both signs and the two doubles
on either side of the first overflow (about 2e307, since `wetBulbC * 9` overflows before the
division, which also tells REQ-FL-004's expression from `wetBulbC * 1.8 + 32`), and the
oracle follows. Why: REQ-FL-004 already made the result `flagF`'s, and REQ-FL-006 is about a
non-finite input, which this is not.

Rejected:
- The REQ-FL-006 form: it reports the input as invalid when the input is finite.

## D-027: The implementation may be in Rust

- Source: Graft, 2026-10-31: Rust rebuilds, proved on this record first
- Cited by: REQ-BU-001, REQ-BU-003

BU-001 to BU-004 named TypeScript and Python only, so a Rust build of this record failed
its static checks whatever it did. Nothing else in the record depends on the language: the
driver protocol is JSON lines, and the edges define number text by ECMAScript's rules, not
the host's. Decision: `lang` may be `"rs"`; a Rust build uses Cargo, edition 2021, the
standard library only and no dependency tables, built offline; its build output stays in
`target/`, outside the size count. Why: the record's point is that any builder can meet it.

Rejected:
- A separate record for Rust: two records drift, and the point is one record.

## D-028: The implementation may be in Go

- Source: Graft, 2026-10-31: Go rebuilds, after D-027 for Rust
- Cited by: REQ-BU-001, REQ-BU-003

As with Rust (D-027), nothing in the record depends on the language but the folder's
rules. Decision: `lang` may be `"go"`; a Go build has a `go.mod` that requires nothing,
no `go.sum` and no `vendor/`, builds with the standard toolchain and no network, puts its
binary in `bin/`, and counts its `.go` files toward the size, tests (`*_test.go`) apart.
Why: Go, TypeScript and Rust cover most new services; the record should admit all three.

Rejected:
- Allow modules from a vendored folder: the builder has no network to fetch them, and a vendored tree is code the record never judged.

## D-029: A byte order mark makes a line bad_request

- Source: Graft reproducibility rounds, 2026-11-05 round 1 and 2026-11-08 rounds 1 and 3 (raw request repro:raw:16)
- Cited by: REQ-IF-009

Nothing said what a request line that starts with U+FEFF gets. Graft's raw pack sends a
valid `flagF` request with the mark in front, alone on standard input, and three blind
builds answered it two ways in three of the rounds scored; duramen's driver protocol leaves
white-space-only lines open but says nothing about a mark before a request, so the record
has to. RFC 8259 lets a parser ignore a mark and forbids sending one; JSON's white space
does not include it. Decision: the mark is part of the line, so the line is not a JSON
object and gets `bad_request` with `id` null (REQ-IF-009). Why: the Errors list already
says a line that is not a JSON object is `bad_request`, D-019 makes malformed requests
errors, and the oracle answered so already (`JSON.parse` rejects the mark and Node's UTF-8
decoding of standard input keeps it); every language's strict JSON parser does the same
unless the builder adds a step to strip it.

Rejected:
- Strip a leading mark and answer the request: adds a step to every driver that strict parsers do not take, and the Errors list would need an exception to say which lines are JSON.

## D-030: wetBulb computes only from -273.15 to 1000 °C

- Source: Graft reproducibility round, 2026-11-08 round 3 (generated request agree:wetBulb#9)
- Cited by: REQ-WB-006

OPEN-WB-001 left results for inputs of enormous magnitude unspecified. Three builds split
on `wetBulb` with `tempC` 1.4831838650267556e+308: `wetBulbC` is finite but
`(wetBulbC * 9) / 5 + 32` overflows, and the oracle could not answer (a non-finite number
in a result). Well before overflow the formula stops meaning anything: from about 1e11 °C
the last-place differences between platforms' `atan` exceed the ±1e-5 tolerance, and the
summary's two decimals can differ before that. Decision: `tempC` from -273.15 (absolute zero) to
1000, inclusive, computes as before; outside, the result is `null` and the summary
`out_of_range:tempC`, with the bounds as constants (REQ-WB-006). OPEN-WB-001 is removed:
within the bounds nothing overflows. `wetBulbF` follows through REQ-WB-005. Why: D-019
makes a value a caller can pass a result, not an error, and REQ-WB-004 already reports an
unusable temperature as a `null` result with its reason in the summary; a new summary word
says which reason. Absolute zero is a physical bound; 1000 °C is far above any air
temperature this library serves and far below where the formula loses precision, and every
existing example, evidence row and property stays inside it.

Rejected:
- A `bad_request` or new error code: the Errors list and D-019 keep errors for malformed requests, and a finite number is a valid value.
- `invalid_input:tempC`: D-026 rejected reporting a finite input as invalid, and a caller should be able to tell a NaN from a temperature out of range.
- Keep computing and pin overflow to null: results between about 1e10 and the overflow would still differ by platform.
